Read-only is harder than it looks

Depending on their flags, arguments and settings, many git commands that read can also write files, start programs or read outside the repository. Each request below ran through plain git and through gitro.

A list of safe commands isn't enough to make git read-only: show --output writes any file, a plain diff saves the index, and diff given two file names prints any file on the disk.

Where the usual safeguards fall short

Agent tools offer a few ways to keep an agent's git use read-only. Each has been bypassed in public, mostly through requests like the ones above.

Approval prompts

A prompt shows only the command. In Cursor's auto-run mode, shell built-ins could set environment variables without a prompt, so a PAGER set earlier ran when the user approved a plain git branch. Fixed in Cursor 2.3 (CVE-2026-22708).

Allow-lists of commands

An allow-list names commands, but their flags decide what they do. Codex CLI's default list trusted git show and git diff, which the first request above exploits: a config file written with --output, then a program started by the next diff. Fixed in Codex CLI 0.95.0 (Pillar Security's write-up).

Git tools for agents

Servers that give agents git as a set of tools pass the agent's arguments on to git. The reference git server for the Model Context Protocol took --output=<file> as the target of its diff (CVE-2025-68144), and another took options in place of revisions (CVE-2026-85626).

Read-only sandboxes

A read-only sandbox blocks writes regardless of flags, which makes it the strongest of the four. It doesn't limit reads: everything mounted is visible, including untracked .env files and tokens in .git/config. Commands allowed to run outside the sandbox, like Codex CLI's allow-list above, bypass it.

How gitro prevents this

  • The caller runs nothing on the repository's machine. It writes a request (a command and its arguments, one per line) and reads the answer. Without a shell, it can't set variables like PAGER or change git's config.
  • Everything not listed is refused. Each command comes from a fixed menu, and each flag from that command's allow-list. git keeps adding flags, and most commands accept any unambiguous abbreviation of one (--cont for --contents), so a list of flags to refuse would always miss some.
  • Arguments can't become options or outside files. An argument can't start with -, and diff checks every name with git's own rule for what's inside the repository.
  • git starts no other program: no pager, external diff, textconv converter, file-watcher hook or signature check, even if the repository's config sets one.
  • Nothing is saved. Each command runs against a copy of the index, so not even diff or status writes to the repository.
  • Untracked secrets stay out. Untracked files appear only by name, never their contents, and remote URLs lose their credentials.
  • Every request is logged. The server logs each one, and -k keeps a copy of each answer. tests/gitro-test.sh checks all of the above against a project configured to start a program wherever git would.

What it doesn't do

  • It shows everything git tracks, including any secret committed to the history.
  • It runs the repository's clean filters, such as Git LFS's, which git needs to read files in the working tree.
  • It answers one request at a time and doesn't limit how many a caller sends.
  • Anything that can write to the request folder can send requests, so give each caller its own folder.
